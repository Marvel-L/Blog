# 发起下载请求

## 发起演进

1. 一开始我们这个系统支持的是 单一发起 即 客户/产品 手动发起 。导致如果要发起 多账户的时候 比较困难

2. 后续为了支持 批量抓取，我们在 原有的状态基础上 即 `packaging_data` 之前增加了 `not_started` 的流程

任务先以 `not_start` 的形式入库, 然后通过 ==后台启动一个协程== 实时监听我们的消息消息内容

**问题:**

1. 为什么不适用 定时任务 而是 使用实时监听的形式 ？

2. 这里如果是多实例的情况下应该怎么办 ? 参考合同项目 只有主实例 跑这些内容 ？ 或者说就拆成定时任务 通过三方平台调度？

   - 常规做法 **通过Redis 租约锁, 抢主实例**

## 限流控制

1. 设计了一个 1分钟 一次的进程级 限流，防止单一进程 打爆 IP 权重限制

2. 使用 Redis 控制对应的月额度限制，每次发起打包任务之前判断是否有可用次数

**问题:**

1. 进程级的限流是怎么控制的 ？

   A : mutex + 令牌桶
   Q : mutex 会频繁加锁，是否有其他更好的办法 ？

   - CAS & Mutex

2. 如果一个 IP 在多个实例上 怎么办 ？

   A. 改成 Redis 控制限流，使用 Set ex 控制分钟级别的限流，注意的是 使用 lua 脚本, 查询和减少是一个原子性操作
